# Контент «Стажёра»: формат задач и правила

Игра «Стажёр» (Codezilla Games) — симулятор стажёра в IT-компании «Кодзилла Софт», который учит программированию.
Игрок проходит общую базу (Intern), выбирает профессию (Backend / Frontend / DevOps, после всех трёх — Fullstack)
и растёт по грейдам Intern → Junior → Junior+ → Middle. **Цель: к концу направления игрок реально умеет всё,
что нужно Middle-разработчику.** Поэтому задачи и теория — настоящие, как на работе, без упрощений до неправды.

Язык: русский, обращение на «ты», живо, без канцелярита. Технические термины — как говорят в индустрии (деплой, PR, прод, ретрай).

## Вселенная

Компания «Кодзилла Софт». Продукты:
- «Ламповый Маркет» — интернет-магазин электроники и ламп (каталог, корзина, заказы, оплата, отзывы). Бэкенд на Python/FastAPI + PostgreSQL, фронт на React + TypeScript, всё в Kubernetes.
- «КофеБот» — внутренний бот заказа кофе в офисе.
- «Кодзилла Трекер» — внутренний таск-трекер.
- Клиентские проекты: сайт доставки пекарни «Батон» (владелица Нина), запись на тренировки фитнес-клуба «Жми» (директор Артур), бронирование переговорок бизнес-центра «Высота» (управляющая Вера).

Персонажи (поле `character` → кто пишет):
- `teamlead` — тимлид **Гена** (добрый, но требовательный) или сеньор **Марина** (строгая на ревью).
- `manager` — продакт **Стас** (торопится, размытые требования) или HR **Оля** (только онбординг в общей базе).
- `qa` — тестировщица **Ира** (дотошная, приносит баги со шагами воспроизведения).
- `devops_colleague` — DevOps **Дима** (дежурит, пишет про инциденты и инфраструктуру).
- `client` — Нина, Артур, Вера или клиент «Лампового Маркета».

`story` — короткий текст тикета/сообщения от лица персонажа, 1–5 предложений, начинается с имени: «Гена: «…»».

## Файл, который ты пишешь

```json
{
  "track": "backend | frontend | devops | common | fullstack",
  "part": "метка части, например b2",
  "topics": [ { "topic_id": "…", "theory": "…" } ],
  "tasks": [ … ]
}
```

`topics` — только темы твоей части (id и grade берутся из `roadmap.json`, не меняй их). `theory` — урок по теме,
который игрок читает перед задачами: 1200–3500 символов, простой текст (абзацы через пустую строку, пункты начинаются с «• »,
примеры кода отдельными строками с отступом 4 пробела). Теория должна покрывать всё, что нужно для задач темы и для реальной работы
на этом грейде: ключевые понятия, как правильно, частые ошибки, команды/синтаксис. Без воды.

## Задача

```json
{
  "task_id": "<topic_id>-NN",            // be-sql-joins-01, нумерация с 01 по порядку сложности
  "topic_id": "…",
  "grade": "intern | junior | junior_plus | middle",   // = grade темы из roadmap.json
  "type": "quiz | find_bug | write_code | code_review | architecture | incident | estimation",
  "difficulty": 1-5,
  "xp_reward": число,                    // строго по формуле ниже
  "time_limit_minutes": число | null,
  "character": "manager | teamlead | qa | client | devops_colleague",
  "story": "…",
  "content": {
    "question": "что именно сделать/ответить",
    "code": "строка | null",
    "language": "python | javascript | typescript | yaml | bash | sql | dockerfile | html | css | jsx | tsx | nginx | hcl | promql | text | null",
    "entry": "имя функции (только для python/javascript с тестами функций)",
    "options": ["…"] | null,
    "correct_answer": "string | number | array",
    "test_cases": [ { "input": …, "expected": … } ] | null
  },
  "explanation": "почему правильный ответ правильный — 3–7 предложений, учит, а не просто констатирует",
  "hints": ["мягкая подсказка", "подсказка сильнее", "почти ответ (необязательно)"]   // 2–4 штуки
}
```

### Сложность, XP, время
- Диапазоны сложности: intern 1–2, junior 1–3, junior_plus 2–4, middle 3–5. Внутри темы задачи идут по возрастанию сложности.
- `xp_reward` = round(base[difficulty] × mult[grade] / 5) × 5; base: 1→20, 2→35, 3→55, 4→80, 5→110; mult: intern 1, junior 1, junior_plus 1.25, middle 1.5.
  (d3 junior = 55, d4 junior_plus = 100, d4 middle = 120, d5 middle = 165.)
- `time_limit_minutes`: у `incident` обязательно 10–30 (прод горит); у `estimation` 10–15; у остальных null (можно 20–60 для middle-задач «к релизу»).

### Junior vs Middle
- Intern/Junior: чёткая инструкция, что сделать и как проверить.
- Junior+: инструкция есть, но нужно самому выбрать подход.
- Middle: размытый тикет как в жизни («после релиза каталог грузится 8 секунд, разберись»), игрок сам понимает, что делать. В `question` всё равно должно быть однозначно, что ответить/сдать.

### Типы задач и правила ответов
- **quiz** — теория. `options` 3–6, `correct_answer` = индекс (с 0). Если верных несколько — массив индексов, и в `question` явно «выбери все верные».
- **architecture** — выбор решения. Контекст и ограничения в `story`/`question`/`code` (схема, метрики, EXPLAIN). `options` 3–5 подхода, `correct_answer` = один индекс. В `explanation` — сравнение компромиссов.
- **incident** — прод упал. В `code` — логи/метрики/вывод команд (`language`: `text` или `bash`). `options` 3–7 (причины или действия), `correct_answer` индекс или массив («выбери все правильные действия»). Логи реалистичные.
- **estimation** — оценка задачи. `options` 5–9 уточняющих вопросов/рисков, `correct_answer` = массив индексов важных (обычно 3–4). В `explanation` — разумная оценка и декомпозиция.
- **code_review** — PR на ревью. `code` — рабочий код с реальными проблемами (производительность, безопасность, читаемость, баги на краях). `options` 4–8 замечаний: настоящие проблемы + правдоподобные, но неверные или вкусовые. `correct_answer` = массив индексов настоящих (2–4).
- **find_bug** — два варианта:
  - *Исполняемый* (python / javascript / sql): `options` = null, `code` = код с багом, `correct_answer` = ПОЛНЫЙ исправленный код, `test_cases` — баговый код падает хотя бы на одном тесте, исправленный проходит все.
  - *С выбором* (для yaml, dockerfile, jsx, bash, nginx, логов и т. п.): `options` 3–6 вариантов диагноза/исправления, `correct_answer` = индекс.
  Баги — типичные для реальной работы: off-by-one, изменяемый аргумент по умолчанию, `=` вместо `==`, забытый `await`, мутация состояния в React, неверный JOIN, отсутствие `ORDER BY`, неправильный отступ в YAML, `latest`-тег, забытый `set -e`, неправильный порт и т. д.
- **write_code** — написать код. `options` = null, `code` = заготовка, `correct_answer` = ПОЛНОЕ эталонное решение (текст, который будет в редакторе). Проверка зависит от языка (ниже).

### Проверка кода (test_cases)
1. **python, функции** — `entry` = имя функции; тест: `{"input": [арг1, арг2], "expected": результат}`. Значения — JSON (числа, строки, bool, null, списки, словари). Кортежи сравниваются как списки. Нельзя передавать функции/объекты — только данные.
2. **python, программа** — `entry` нет; тест: `{"input": "строки ввода через \n", "expected": "точный вывод"}` (сравнение без хвостовых пробелов).
3. **javascript** — только функции, `entry` обязателен, функция может быть `async` (результат ожидается). Чистый JS (ES2022): без DOM, `require/import`, `fetch`, таймеров. Асинхронность имитируй через `Promise.resolve(...)`. Колбэки нельзя передать в тестах — вспомогательные функции объявляй в самом коде.
4. **sql** (диалект SQLite, стандартный SQL) — `code` содержит схему и данные (`CREATE TABLE`, `INSERT`) и комментарий «-- твой запрос ниже»; `correct_answer` — весь текст + запрос; проверяется результат ПОСЛЕДНЕГО запроса: `{"input": null, "expected": [[значения строки], …]}` (одного теста достаточно). Если строк больше одной — обязательно `ORDER BY`. Можно рассказывать про PostgreSQL в сюжете, но исполняемый SQL должен работать в SQLite (без `ILIKE`, `SERIAL`, `::`).
5. **Статические проверки** (yaml, dockerfile, bash, typescript, tsx, jsx, html, css, nginx, hcl — Terraform, promql) — минимум 3 теста вида
   `{"input": "что проверяем (для игрока)", "expected": {"regex": "…", "flags": "im"}}` или `{"not_regex": "…"}`.
   Регулярки должны принимать разумные варианты правильного ответа (`\s*`, `['"]?`, флаг `i`), без именованных групп.
   Эталон проходит все проверки, заготовка — не все. Эталон синтаксически корректен (YAML парсится, bash проходит `bash -n`).

Код в задачах (кроме намеренных багов) — рабочий и идиоматичный. Во фрагментах для quiz/code_review/architecture можно
использовать настоящие библиотеки (FastAPI, SQLAlchemy, React, kubectl…), но код должен быть синтаксически верным.

### Игровой Python (для исполняемых python-задач)
В игре свой интерпретатор Python. В исполняемых задачах (write_code, find_bug без options) используй только:
- инструкции: присваивание (в т. ч. `a, b = …`, `+=`, аннотации типов), if/elif/else, while, for, break/continue/pass, def (значения по умолчанию, `*args`, `**kwargs`, вложенные функции и замыкания, `nonlocal`/`global`), return, class (одно наследование, `super()`, `@property`, `@staticmethod`, `@classmethod`, свои декораторы-функции), try/except/else/finally, raise, assert, del, lambda;
- выражения: генераторы списков/словарей/множеств, `x if c else y`, срезы, f-строки (в т. ч. `{x:.2f}`), `in`, `is None`, цепочки сравнений, распаковка `*`;
- встроенные: print input len range int float str bool list dict set tuple sorted reversed min max sum abs round enumerate zip map filter any all isinstance repr type hasattr getattr setattr divmod pow chr ord super и стандартные исключения;
- методы строк, списков, словарей, множеств (основные); `import math`, `import json`, `from collections import Counter, defaultdict`.
Нельзя: with, yield/генераторы-функции, async/await, match, `:=`, `%`-форматирование, другие импорты. (async/генераторы/with изучаются через quiz/code_review.)

### Баланс
- В каждой теме 3–5 задач (обычно 4), минимум 2 разных типа. Во всей своей части используй все 7 типов.
- Практика важнее теории: на тему обычно 1 quiz максимум, остальное — задачи «руками» (write_code / find_bug / code_review) и ситуации (incident / architecture / estimation) там, где они естественны.
- Не дублируй задачи между темами. Факты — точные и актуальные (2026 год).

## Как писать
Собирай файл Python-скриптом `Tools/Content/gen/<part>.py` (словари и строки в тройных кавычках → `json.dump(..., ensure_ascii=False, indent=1)`): так проще править код в задачах без ошибок экранирования. Пиши по одной теме за раз.

## Проверка
После записи файла запусти: `python3 Tools/Content/spec/validate.py <твой файл> --fix` и исправляй, пока ошибок не станет 0
(`--fix` сам поправит xp_reward). Предупреждения тоже посмотри. Примеры всех типов — в `spec/examples.json`.
